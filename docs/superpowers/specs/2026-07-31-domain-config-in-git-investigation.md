# Investigation: storing domain configuration in git

**Date:** 2026-07-31
**Status:** Investigation complete — owner decisions recorded (§7), ready for implementation planning
**Issue:** [#1095 — Investigation: Figure out how to store domain configuration in git](https://github.com/Anglesite/Anglesite/issues/1095)

## Problem

Anglesite manages DNS records and Cloudflare Workers-related configuration on the owner's
behalf, but almost none of that configuration is serialized into the site's repo. It lives
only in Cloudflare's control plane, so nothing links the configuration to the code that
depends on it, drift is invisible until something breaks, and no automatic validation is
possible. #1095 asks how that configuration should be stored in git.

## 1. Inventory: where domain/edge configuration lives today

### Live-only (Cloudflare control plane, no local footprint)

- **DNS records** — everything created via the Domain sheet (`DomainOperationsService`),
  Apple Intents (`DomainIntents.swift`), Bluesky/Google verification, and Email Routing.
  `DomainOperations` writes straight through to the API with no local mirror; the
  domain–DNS integration design (2026-07-05) explicitly framed DNS as "live Cloudflare
  API calls … with no site-source footprint at all."
- **Zone hardening state** — `CloudflareZoneState` (DNSSEC, SSL mode, Always-Use-HTTPS,
  HSTS, CAA/MX/SPF/DMARC, Bot Fight Mode, WAF custom rules, Speed Brain, ECH, zstd,
  Page Shield, Onion Routing) is a complete desired-state model that is fetched, graded
  by `SecurityAudit`, applied by the Harden flow, and then **discarded** — never
  serialized. `HardenModel` persists nothing.
- **Email DNS plans** — `EmailSetupPlanner.DNSPlan` is already a declarative record set
  (MX/SPF/DKIM/DMARC templates per provider) but is handed to the UI and never lands on
  disk (#769).
- Email Routing rules, Turnstile widgets, Zaraz config, workers.dev subdomain state,
  Workers Custom Domain attachments (only the `CF_DOMAIN_ATTACHED=<host>` breadcrumb
  survives).

### Git-tracked (`Source/`)

- **`.site-config`** — flat shell-style `KEY=value`. Domain-adjacent keys: `DOMAIN`,
  `DOMAIN_CHOICE`, `SITE_URL`, `SITE_DOMAIN` (legacy), `CF_PROJECT_NAME`,
  `CF_DOMAIN_ATTACHED`, `CF_WORKER_DEPLOYED`, `CF_WORKER_PROVISIONED`,
  `CF_WEB_ANALYTICS_TOKEN`. No schema, no versioning, no nesting; nominally
  "template-owned" (`SiteConfigFile.swift`) yet the `CF_*` keys are app-written deploy
  state — the ownership story has already blurred.
- **`wrangler.toml`** — generated by `WorkerComposition.generateWranglerToml`, git-tracked,
  and **write-only by design**: there is no reader that reconstructs the feature list or
  resource IDs from an existing file (`WorkerNameRename.swift` does line surgery instead;
  `SocialWorkerProvisionCommand.readPersistedResources` is a string-scrape fallback).
- `redirects.json`, `src/data/robots-config.json`, `src/data/licensing.json` — versioned,
  app-managed, human-editable JSON with a Swift store on one side and a TypeScript
  consumer in the template on the other. **This trio is the cleanest precedent.**

### App-owned, never committed (`Config/settings.plist` and friends)

- `activeWorkerIDs` / `lastDeployedWorkerIDs` — the owner's worker activation choices and
  the deploy-diff baseline (#709).
- `provisionedWorkerResources` — D1 database ID, KV namespace ID, R2 bucket names, queue
  names. Account-scoped resource identity.
- `last-deployed-routes.json`, `inboxCaptureAccountID`/`inboxCaptureKVNamespaceID`, etc.

### Never on disk

Cloudflare API token (Keychain), Turnstile secret (Keychain → Worker secret). Correct;
unchanged by this investigation.

## 2. The drift this split already causes

These are shipped bugs and documented hazards, not hypotheticals:

- **#1077 / #1124 / #1085** — `DOMAIN` written to git but nothing acted on it; then two
  git-stored keys (`SITE_URL` vs `DOMAIN`) disagreed about precedence; then a site's
  ActivityPub actor resolved to a dead custom domain. All are declared-vs-live divergence.
- **#744 / PR #829** — worker activation lives in `Config/`, but the container runtime
  clones **`Source/` only**, so a headless deploy can't see it. #829's workaround (resolve
  descriptors from the catalog disk cache so headless deploys don't regenerate
  `wrangler.toml` without GUI-written routes) is an explicit patch over this gap.
- **#709 §6** — the earlier attempt to make git-tracked `wrangler.toml` the source of
  truth for resource IDs broke: regenerating it from a reduced feature set erased IDs for
  resources that still existed on Cloudflare.
- **#701** — the deploy skill and the template drifted over which wrangler file even
  existed.
- **`DeployCoordinator.resolveSiteURL`** documents the trust model bluntly: a configured
  domain "is never verified to be live."

## 3. Constraints (already-settled decisions that bind the design)

1. **The `Source/` vs `Config/` boundary is spec-level** (package-model design §8, #402):
   repo-artifact preferences belong in `Source/`; account tokens and app-private state in
   `Config/`, never git. Anything the deploy pipeline or container needs **must** be in
   `Source/`, because the runtime never sees `Config/`.
2. **Secrets and account-scoped identity never enter git.** Tokens/secrets in Keychain;
   resource IDs (D1/KV/R2) deliberately moved to `Config/` after the #709 failure.
3. **DNS records are multi-owner.** MX/SPF/TXT are contested between Harden, Email
   Routing, iCloud Custom Email Domains, and pre-existing third-party providers. Settled
   posture (free-services design §6, §13): abort with an explanation rather than clobber,
   and namespace what the app manages.
4. **Cloudflare is the only v1 deploy target, but a seam is coming** (#334, #1015). A
   git-stored schema should not be Cloudflare-shaped at the top level.
5. **Reconciliation already has an idiom** — read-only audit scorecard (#406), then
   plan → preview exact diff → apply on consent → re-audit (#407); create-if-absent
   idempotency; never silently take over someone else's resource (#740, #1077 conflict
   arm). And per the "app advises" rule: auto-apply where the app knows the right answer,
   ask (in owner terms, not git terms) where it doesn't.
6. **Git is the source of truth (#72)** — whatever is stored must survive hand edits and
   out-of-app clones; `SiteConfigFile` already commits to round-trip-safe edits.

## 4. Options considered

### A. Extend `.site-config` with more flat keys — rejected

No nesting (a DNS record is a 5-field tuple), no schema or versioning, and the
template-owned vs app-owned split in one file is already muddy. Encoding record sets in
shell KV means inventing an ad-hoc encoding inside an encoding.

### B. Make `wrangler.toml` the source of truth — rejected

Proven failure (#709 §6). It is generate-only, wrangler owns its schema (no place for
DNS records or zone settings), and it is maximally Cloudflare-shaped — the opposite of
what the #1015 deploy-target seam wants.

### C. Adopt a standard IaC tool (Terraform / Pulumi / octoDNS zone files) — rejected

Adds a heavyweight dependency (needs explicit approval per CONTRIBUTING) and a second
reconciliation engine with its own state files, designed for operators. Anglesite's
owners are non-technical; the app is the operator. Terraform state files in git would
also re-introduce the account-scoped-identity-in-git problem deliberately avoided in #709.
Standard formats remain useful as *export* targets later, not as the store.

### D. Versioned, provider-agnostic JSON declaration in `Source/` — **recommended**

Follow the `redirects.json` / `robots-config.json` / `licensing.json` precedent: one
schema-versioned JSON file in `Source/`, a Swift store in `AnglesiteCore`, readable by the
template/scripts where needed, hand-editable, and diffable in git.

## 5. Recommendation

### 5.1 Core principle: declare intent in git; keep identity and observation out

Split the state into three categories with different homes:

| Category | Examples | Home |
|---|---|---|
| **Declared intent** (portable, owner-meaningful) | hostname + attachment intent, managed DNS records, zone hardening posture, email provider choice, active worker set | **`Source/anglesite.json`** (new, git) |
| **Account identity** (provider/account-scoped) | zone ID, account ID, D1/KV/R2/queue IDs, tokens, secrets | `Config/` + Keychain (unchanged) |
| **Observed state** (what's actually live) | audit results, last-deployed snapshots | live reads + `Config/` caches (unchanged) |

Drift then has a precise definition — declared ≠ observed — and validation is a pure
diff, exactly the shape `SecurityAudit` already computes for hardening.

### 5.2 `Source/anglesite.json` (sketch)

```jsonc
{
  "version": 1,
  "domain": {
    "hostname": "example.com",        // replaces DOMAIN/.site-config precedence dance
    "choice": "transfer",              // buy | transfer | later
    "attach": true                     // intent; CF_DOMAIN_ATTACHED stays the receipt
  },
  "dns": {
    // Records Anglesite created and therefore owns. Never a mirror of the whole zone.
    "managedRecords": [
      { "type": "MX",  "name": "@", "content": "mx01.mail.icloud.com", "priority": 10,
        "purpose": "email:icloud" },
      { "type": "TXT", "name": "_atproto", "content": "did=did:plc:…",
        "purpose": "verification:bluesky" }
    ]
  },
  "edge": {
    // Desired hardening posture — the Harden plan, serialized. Provider-agnostic
    // names at this level; Cloudflare-only knobs under a provider key.
    "dnssec": true,
    "alwaysUseHTTPS": true,
    "hsts": { "maxAge": 31536000, "includeSubdomains": true, "preload": false },
    "cloudflare": { "botFightMode": true, "wafRules": [ /* description+expression+action */ ] }
  },
  "email": { "provider": "icloud", "dmarcReportEmail": "…" },
  "workers": {
    "active": ["webmention-receive", "micropub"]   // moves out of Config/ (see 5.4)
  }
}
```

Explicitly **not** in the file: secrets, tokens, zone/account IDs, provisioned resource
IDs, and unmanaged records (the owner's pre-existing DNS is never mirrored, so the app
never appears to claim it).

### 5.3 Managed-record ownership marking

To partition Anglesite-managed records from external ones on the Cloudflare side, stamp
records the app creates using the DNS record `comment` field (e.g.
`anglesite:email:icloud`), mirroring the `purpose` in `anglesite.json`. Reconciliation then
has both sides of the join: declared records carry a purpose; live records carry the
same tag. Untagged live records are external by definition and are never touched —
the abort-don't-clobber posture falls out of the data model. (Zaraz slice §10 already
established the namespaced-entries idiom.)

### 5.4 Worker activation moves to git; resource IDs do not

`workers.active` (the owner's intent) belongs in `Source/` — it is exactly the state
#744 and #829 needed in the container and couldn't have. `provisionedWorkerResources`
stays in `Config/`: the #709 lesson is that *identity* in git gets destroyed by
regeneration, but *intent* in git is what regeneration should be driven from.
`Config/settings.plist.activeWorkerIDs` becomes a migration source, then a dead field.

### 5.5 Write-through, reconcile, validate

- **Write-through:** every existing writer updates the declaration at the moment it acts —
  `DomainOperations.addRecord/deleteRecord`, `HardenExecutor` (apply → serialize the
  applied plan), `EmailSetupPlanner` apply (its `DNSPlan` becomes the first producer,
  resolving the #769 persistence gap), `CustomDomainAttachCommand`, the Workers Settings
  tab toggle. Same transaction shape as `redirects.json`.
- **Reconcile (app-side):** a `DomainConfigAudit` diffing declared vs `CloudflareZoneState`
  + `listDNSRecords`, surfaced like the Security scorecard. Remediation reuses the Harden
  idiom: auto-apply for unambiguous app-owned drift (a managed record missing), a
  consequences-phrased owner question for anything contested (an MX conflict), never a
  git/diff-phrased one.
- **Validate (deploy-time):** the app-side deploy path gains a cheap declared-vs-live
  check before `wrangler deploy` (the same slot `checkWorkerNameConflict` occupies).
  `pre-deploy-check.ts` stays network-free; at most it gains a *structural* check that
  `anglesite.json` parses and is schema-valid, folded into the versioned scan envelope
  (#742). Hand-edited-file tolerance: unknown keys are preserved, invalid files fail
  with a fix-it, matching `SiteConfigFile`'s round-trip rule.

### 5.6 Migration and compatibility

- `DOMAIN`, `DOMAIN_CHOICE` migrate into `anglesite.json` on first write; `.site-config`
  keys remain readable (legacy fallback) for out-of-app clones until a major template
  rev. `SITE_URL` and the `CF_*` deploy receipts stay where they are — they are
  observed/receipt state, not intent, and moving them is churn without benefit.
- Sites without `anglesite.json` behave exactly as today (all fields optional, absent file
  = no declarations). No paired sidecar PR: this is app + template only, no MCP schema
  change. No catalog change required (worker IDs already come from `catalog.json`).

## 6. Suggested implementation slices (follow-up issues)

1. **Schema + stores** — `DomainConfig` model, Swift `DomainConfigStore` (round-trip-safe,
   unknown-key-preserving), template-side reader, schema doc. Ships inert.
2. **Write-through** — DNS sheet, Harden, custom-domain attach, email planner apply (with
   its Settings surface, #769) all update the declaration; record-comment stamping.
3. **Drift audit + reconcile UI** — `DomainConfigAudit`, scorecard surface, Harden-idiom
   remediation.
4. **Worker activation to `Source/`** — `workers.active` in `anglesite.json`, migration from
   `Config/`, headless-deploy path reads it (retiring the #829 cache workaround). Per the
   owner decision below, this slice starts with its own timing investigation: map the
   read/write ordering hazards on the deploy hot path (GUI deploy vs headless deploy vs a
   mid-deploy Settings toggle; stale clones in the container; regeneration racing a hand
   edit) before wiring anything, and ship behind a fallback — if `anglesite.json` is
   absent, unparsable, or older than the `Config/` state it migrated from, the deploy path
   falls back to today's `Config/settings.plist.activeWorkerIDs` + #829 cache behavior
   rather than failing or deploying a reduced worker set.
5. **Deploy-time validation** — pre-deploy declared-vs-live check app-side; structural
   check in the scan envelope.

## 7. Owner decisions (2026-07-31)

The three open questions from the initial writeup were answered by the owner:

1. **File name/location** — the broader **`Source/anglesite.json`**, so the file can later
   absorb other app-managed intent beyond domain configuration. All references in this doc
   use that name.
2. **How much of Harden's posture to declare** — **serialize exactly the applied plan**,
   nothing aspirational. An exact record of what the app actually did is what makes the
   file useful for debugging errors and bug reports: a declared entry always corresponds
   to a real write the app performed.
3. **Slice 4 (worker activation to git)** — proceed, but **investigate timing issues
   further during implementation and keep a fallback** to the current `Config/`-based
   behavior (see slice 4 above for the concrete shape).
